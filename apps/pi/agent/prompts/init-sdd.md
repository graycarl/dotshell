请在 ${1:-当前项目根目录} 中初始化 SDD（Spec-Driven Development，规格驱动开发）工作流。按以下步骤执行：

## 1. 创建目录结构

在项目根目录创建（若已存在则跳过，并放入 `.gitkeep` 占位）：

```
specs/            # 功能规格（用户视角，写代码前必须先写）
handbook/         # 用户使用说明书（HTML + 内联 SVG 截图）
docs/decisions/   # 关键技术决策记录（ADR 风格）
```

## 2. 将开发流程规范写入项目入口文档

在 `AGENTS.md`（不存在则创建）的开头显眼位置（紧跟文件引言之后）加入一节「开发流程规范（Spec 先行，写代码前必读）」，内容如下（可按项目语言习惯微调措辞，但语义不得削弱）：

---

本项目采用 **spec 驱动开发**，严格按以下顺序推进，**不允许跳过文档直接写代码**：

1. **`specs/*.md` —— 功能规格（先写）**
   - 从**用户角度**描述需求：功能是什么、用户怎么操作、看到什么、边界情况如何表现。
   - 每个功能一份 spec（如 `specs/tunnel-list.md`），不写实现细节（架构/代码结构放 `docs/decisions/`）。
2. **`handbook/*.html` —— 用户使用说明书（与 spec 配套）**
   - 面向最终用户的详细操作手册，**带 SVG 截图**（用内联 SVG 模拟界面截图，不依赖真机截图）。
   - 与对应 spec 保持同步：spec 描述的功能必须能在 handbook 中找到对应操作说明。
3. **`docs/decisions/*.md` —— 关键技术决策**
   - 记录「为什么这么做」：方案选型、取舍理由、被否决的备选方案（参照 ADR 风格）。
   - 与代码强相关的架构决策都放这里。
4. **最后才写代码。**

**迭代规则**：后续任何功能新增/变更，**必须先改 spec 与 handbook，再改代码**；
spec / handbook 是验收基准，代码行为与 spec 冲突时以 spec 为准（若 spec 本身有误，先修 spec）。
技术方案变更时同步更新 `docs/decisions/`。

---

同时把 `specs/`、`handbook/`、`docs/decisions/` 补充进 AGENTS.md 的仓库结构说明（若有该节）。

## 3. 验证与汇报

- 确认三个目录已创建、AGENTS.md 更新完成；
- 若 AGENTS.md 中已有与之冲突的开发流程描述，向我指出冲突点并给出合并建议，不要静默覆盖；
- 最后简要汇报改动清单，并建议第一份 spec 的选题（从项目核心功能切入）。
