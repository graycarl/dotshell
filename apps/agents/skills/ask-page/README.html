skill · ask-page

一份 HTML，
把「审阅」从终端里拿出来

Agent 写正文 → 脚本拼成一份自包含的本地网页 → 用户在浏览器里逐条批注、 在选择题里选一个 → 点「复制结果」→ 粘回对话。没有服务进程、没有端口、没有令牌，产物就是一个文件。

01为什么要有它

终端适合「一问一答」，不适合「审阅」。凡是需要读长文、逐条标注、来回比对的确认动作，塞进 TUI 都会变形。

进入 ask-page

内容需要「被审阅」

方案 / 计划 / 文档 / diff / 报告要用户拍板；需要逐条写批注、圈重点；或者让他从几个方案里挑一个。

留在终端

只需要「一个答案」

要么 A 要么 B、需要一小段文字或一个文件名 —— 直接问，或 ask_user。

不要为了用而用。起页面、开浏览器、切窗口粘贴，这一串动作本身就是成本；一句话能问清楚就别用。

02整体形状：一条闭环，没有中间件

上一版是「CLI + HTTP 服务 + 浏览器 + 轮询」，这一版把中间那两层全删了：文件系统是唯一的交接点。

交接点 ①

磁盘

plan.body.html（你写的）和 plan.html（产物）。没有共享状态、没有数据库。

交接点 ②

剪贴板

浏览器写、用户读、对话收。它是唯一「结构化结果」跨越进程的方式。

核心

没有中间件

没有端口、令牌、Origin 校验、状态机、退出码、daemon 和归档。

03一次确认的时序：四条泳道

注意第 ③ 步之后 agent 就结束了本轮。这里没有「等待」，因为已经没有东西可以等 —— 用户的下一条消息就是结果。

04怎么拼出来：三个源文件 → 一个产物

机制（CSS/JS）和内容分开存放，但产物必须是一个文件 —— 这样它才能被随便拷贝、邮件、放进归档。

一个真实的坑：内联脚本里如果出现字面量 </script>（哪怕在注释里），HTML 解析器会当场截断脚本，页面静默失效。ask_page.py 在构建时会检查并直接报错。

05删掉 server，失去了什么、换回了什么

上一版的能力不是白来的 —— 每一项都绑着端口、令牌和进程。这里逐项算账。

换回来的东西同样实在：不用开端口（不会被防火墙/公司策略拦）、不用管令牌（URL 不再是秘密）、不会残留 daemon、不用清理状态目录、不用考虑并发和幂等 —— 因为这些问题的载体都不存在了。

06草稿模型：一张会演进的清单，不是一次性表单

用户的心智不是「提交一次表单」，而是一张随页面演进的待办清单：改好的删掉、没改好的留着、有新想法再加一条。所以草稿跨轮次保留，只有用户自己能删。

选择题的答案住在同一份草稿里，只是没有「已提交」圆点：它在页面里是选中态，刷新、换版本都还在。

机制

每个变更立刻落盘

没有「保存」按钮。加一条、删一条、改一次选择，都当场写回 localStorage，刷新不丢。

代价

重复提交旧意见

用户没删的批注会再次被导出。页面用「已提交」圆点和顶部横幅提示，导出后由用户自己判断要不要清掉。

对 agent 的硬约束：重写页面时 anchor 必须稳定（plan-3 永远指同一段话）。改了 anchor，用户的旧批注会变成「位置已失效」—— 它们仍会被导出，但位置信息丢了。 同理，选择题的 data-pi-option 名字也是契约：改了名字，用户选过的答案会静默消失（页面里已经没有这道题，就不再导出）。

07导出格式：Markdown + 哨兵，没有 JSON

上一版必须有 JSON，因为消费者是 shell；现在消费者是 LLM —— 它读 Markdown 和读 JSON 一样准。少一份结构化副本，就少一半 token、也少一处可能不一致的地方。

三条解析规则

  1. 取 <!-- ask-page-result 与 <!-- /ask-page-result --> 之间的内容
  2. ## 选择 小节：每行 - 名称（id）：标签（值） 是一道题的答案；没有这一小节 = 用户没选
  3. 每个 ### [锚点] 标签 起一条批注：正文到下一个 > 行 / 下一个 ### [ / 哨兵为止
情况输出长什么样
一道题都没答## 选择 整个小节不出现
一条批注都没写## 批注 整个小节不出现 —— 两者都空就只剩哨兵两行
anchor 在新页面里消失了标题变成 ### [plan-9] 标签 ⚠ 位置已失效，批注仍然导出
选项的那道题被删了旧答案不导出（题都没了，答案就是噪声）
为什么不给一个「纯 JSON」的兜底按钮？ 因为它会让 agent 有时拿到结构化、有时拿到文本，反而增加判断成本。出口只有一个，规则就只有一套。

08多轮迭代：同一个 id，手动刷新

没有 server 就没有推送。file:// 下页面也无法监视磁盘变化（fetch 被 CORS 拦）。所以刷新是一件显式的事：改正文 → new → 点「↻」。

不要给新版本换文件名。plan-v2.html 会让 pageId 变成 plan-v2，上一轮的草稿瞬间「人间蒸发」（其实还在，只是 key 对不上了）。id 和 anchor 都是跨轮次契约。

09页面怎么写：声明式标记

Agent 不写 JS。它只在正文里放 data-pi-* 标记，内联的脚本负责把标记变成交互、再变成导出文本。

选项也可以是卡片。给容器写 data-pi-option、给里面的元素写 data-pi-value， 整块内容就是一个选项 —— 标题、说明、代码都能放。脚本只负责加圆点和点击，不动你的结构； 卡片里的链接和按钮照常工作。
离线假设：页面在 file:// 下打开，不要引用 CDN；外部图片和 plan.html 放同一目录用相对路径。同理，<script type="module"> 在 file:// 下会被 CORS 拦，所以脚本必须是普通 IIFE。

10localStorage 的现实：一个共享的 origin

实测：file:// 下的 localStorage 可用，但所有本地文件共享同一个 origin —— A 页面写的 key，B 页面能读到。所以草稿必须按 pageId 做命名空间。

降级路径：隐私模式或「阻止所有 Cookie」会禁用存储。页面检测到异常后把状态栏改成「草稿无法保存」，但导出始终可用 —— 用户只是会失去刷新恢复的能力。

11剪贴板：唯一的外部依赖，所以要三级降级

「复制」是这套设计里唯一接触浏览器 API 的地方，也是唯一可能失败的地方。失败不能让用户丢结果。

12取舍与坑

取舍 1

去掉自动回传

放弃「agent 自己拿到结构化结果」。换来：没有进程、没有端口、没有超时语义，也不会在用户离开时留下守护进程。粘贴换掉了一整套运行期状态。

取舍 2

去掉图片上传

图片要真正交给 agent，只能走 base64 —— 一张普通截图就是十万级 token，还会撑爆 localStorage。而对话本身就支持贴图，页面再插一脚是重复劳动。

取舍 3

去掉 JSON 双份

消费者从 shell 变成 LLM，严格结构化的价值骤降。单份 Markdown 让 token 减半，也消除了「两份内容打架」的可能。

取舍 4

草稿永不自动清理

放弃「每轮干净开始」。换来：用户不必重写没改好的意见。代价是旧批注可能被重复提交 —— 用「已提交」标记提示，把决定权交给用户。

取舍 5

机制内联进产物

放弃「页面与脚本分离」的清爽源码结构。换来：产物是单文件、agent 不会改坏机制。代价是调试要看 40 KB 的合并文件。

取舍 6

刷新是显式的

放弃「自动感知更新」。换来：不需要常驻进程去推版本。用户点一下 ↻，或者干脆重新打开。

常见坑

  • stdout 只有一行 JSON（built / opened / list / error），进度都在 stderr。
  • id 和 anchor 都是跨轮次契约：换 id 丢草稿，换 anchor 丢位置。
  • agent 写完页面就结束本轮，不要试图等待 —— 没有东西可等。
  • 用户可能只写几条批注，也可能什么都不写就关掉，两种都要能处理。
  • 选择题不选是常态：## 选择 没出现就代表用户跳过了，不要当成出错。
  • 选项 id 改名 = 静默丢答案，而且不会有「位置已失效」之类的提示 —— 这一条比 anchor 更隐蔽。
  • new 会覆盖 plan.html，但不动 localStorage；刷新后草稿还在。
  • 别在脚本里写字面量 </script>（包括注释），否则页面静默失效；构建期会拦。
  • 页面不联网也离线可用，所以样式、图标、字体都必须内联或用系统字体。
  • 任务结束后 .pi/ask-page/ 可以直接删；它不该进 git。
