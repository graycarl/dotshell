# 计划（需求分析与方案设计）

进入计划模式。**唯一允许的写操作是维护 plan 文档**（路径见下）；除此之外**禁止使用
write/edit 修改任何文件**——包括"为建文档而顺手改代码"、改 `.gitignore` 这类动作。

## 目标

1) 分析需求中需要被澄清的问题点，沿决策树逐分支深入，直到所有细节被澄清。
2) 分析现有代码实现，结合一些必要的技术调研，提出可行方案，并继续讨论需求中的不确定点。
3) 产出一份**可 review 的 plan 文档**；在用户确认达成共识之前**不执行**。

## 一、先落盘，再提问

**在问第一个澄清问题之前**，先建好 plan 文档：

- 路径：`<project-root>/.pi/plans/<date>/plan-<slug>.md`
  - `<project-root>`：`git rev-parse --show-toplevel`，失败则用当前目录
  - `<date>`：`date +%F`（如 `2026-11-26`）；目录不存在就 `mkdir -p`
  - `<slug>`：英文小写中划线，2–5 个词，取自需求核心名词（如 `plan-skill-marked`）
  - **同名已存在就复用并继续更新**，不新建；跨天续写沿用旧日期目录的文件，
    并在文档头注明本次更新时间
- 初稿内容：需求描述 + 已核实的事实 + 待澄清问题清单（每条带推荐答案）
- 建好后打开一次（Marked 会监听文件变化，后续更新自动刷新）：

```bash
bash ~/.pi/agent/skills/plan/scripts/open-plan.sh "$PLAN_FILE"
```

退出码非 0 表示 Marked 不可用：**不要换别的 App 打开**，只在对话里报告文档路径，
流程照常继续。

## 二、边聊边写

| 时机 | 动作 |
|---|---|
| 需求初步理解后、**问第一个问题之前** | `write` 初稿，然后打开 Marked（见上） |
| 每个关键决策达成后 | `edit` 追加一行「决策记录 Dn」，并勾掉对应疑问 |
| 方案定稿时 | `edit` 补全「方案设计 / 改动清单 / 任务拆解」，状态改「待确认」 |
| 用户确认共识 | 状态改「已确认」，文档保留在 `.pi/plans/`，再退出计划模式 |

不要把内容攒到最后一次性输出——用户要能在 Marked 里看到方案是怎么长出来的，
跑偏了能尽早打断。

### 文档模板

```markdown
# <需求标题>

> **状态：Draft / 待确认 / 已确认** — <YYYY-MM-DD HH:MM>
> 本文件由 plan 模式实时维护，结论变更即回写。

## 1 需求描述        <!-- 用户原话 + 复述 + 边界（不做什么） -->
## 2 事实调研        <!-- 表格：已核实的客观事实，含出处（文件路径/命令输出/文档） -->
## 3 方案设计        <!-- 选型对比表 + 最终选择及理由 -->
## 4 决策记录        <!-- 表格：Dn | 决策点 | 结论 | 理由，追加式 -->
## 5 改动清单        <!-- 表格：文件 → 改什么 -->
## 6 待确认问题      <!-- 带推荐答案；已定的划掉 -->
## 7 任务拆解        <!-- - [ ] 可执行条目，含文件路径 -->
```

## 三、交互要求

### 一次一问

- 直接向用户提问。
- 每次**只问一个问题**，等用户回答后再继续下一个。一次抛出多个问题会让用户不知所措。
- 沿着决策树逐分支深入：先解决上游决策，再根据答案走向下游分支，直到所有分支都被理清。
- 每个问题都要附带你的**推荐答案**，并给出相关背景信息和各选项的优缺点，帮助用户做出选择。
- 澄清问题尽量给出可选项，而不是开放式问题。
- 用户一旦回答，立刻把结论写进文档（决策记录 + 划掉疑问），再问下一个。

### 充分调研

你可以使用 bash、read 等工具来探索本地代码库，使用 context7 查询技术文档，使用 github cli 查询 GitHub 仓库，或者使用 exa search 来搜索网络;

- 尽量主动探索一些**事实**，包括一些技术细节、可能的方案及其优缺点等，而不是直接问用户。
- 只把真正的**决策权**交还给用户——即那些无法通过调研查找确定、需要用户主观判断的选择。
- 事实一旦核实就写进文档「事实调研」表格，并注明出处。

### 确认闸门

- 在用户明确确认"我们已达成共识"之前，**不要开始实现**。
- 最终方案需包含 **需求描述**、**方案设计**、**任务拆解** 三部分（对应文档 §1 / §3 / §7）。

## 退出计划模式

当方案定稿、用户在文档里 review 过后明确确认共识：

1) **收口检查**——以下几条必须同时满足，缺任何一条就先补齐再退出：
   - §1 需求描述 / §3 方案设计 / §4 决策记录 / §5 改动清单 / §7 任务拆解 都已填满
   - §6 待确认问题没有残留的未划掉条目
   - 最后一轮聊出来的结论已回写，文档与最终共识一致
2) 把文档状态改为「已确认」（附时间戳）
3) 向用户确认是否退出计划模式，若用户确认则退出，并按「动工前置」进入实现；
   否则继续进行需求分析和方案设计

## 动工前置（退出计划模式后）

用户确认共识后，**第一个动作不是改代码，而是重读方案文档**：

1) 用 `read` 工具完整读取 plan 文档——不要凭对话记忆复述
2) 读完输出 5 行以内「开工对齐」，让用户低成本纠偏：
   - 目标：
   - 要改的文件（按顺序）：
   - 明确不做：
   - 验证方式：
3) 对齐后再开始改动

执行中发现文档与先前聊天不一致时，**以文档为准**；若文档确实错了，先更新文档并告知
用户，不要只改代码。跨 session 实现（本 skill 未被加载）时，先 `ls .pi/plans/*/`
找到对应文档再读。
